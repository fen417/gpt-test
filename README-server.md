# SECTOR 09: один сервер Northflank Sandbox

В версии 0.14 сетевой матч рассчитывает один Node.js-процесс. Все игроки, включая создателя комнаты, подключаются к нему по одному WebSocket. Клиент и игровые ресурсы остаются на GitHub Pages. Одиночный бой с ботами работает в браузере отдельно.

## Развёртывание без собственного ПК

1. В Northflank выберите **Sandbox Free**. Подключите GitHub через официальный интерфейс Northflank и разрешите доступ только к `fen417/gpt-test`. Игровому клиенту GitHub-токен не нужен.
2. Создайте один проект. Начальный выбор для Приднестровья — **Europe West Frankfurt** (`europe-west-frankfurt`). Это географически обоснованный выбор, а не результат измерения пинга. В официальном списке также есть Zurich, Netherlands и Europe West. Доступность именно вашему Sandbox проверяйте в форме создания проекта; регион проекта впоследствии не меняется. Не создавайте несколько работающих сервисов для сравнения. [Регионы Northflank](https://northflank.com/docs/v1/application/run/deploy-to-a-region).
3. Создайте **Combined Service**: репозиторий `fen417/gpt-test`, ветка `main`, автоматическое развёртывание новых коммитов, сборка **Dockerfile**, путь `/Dockerfile`, контекст `/`. Один runtime-процесс, одна реплика. Docker собирает только сервер и общие модули; клиент собирается своим GitHub Actions workflow.
4. Выберите **`nf-compute-50` — 0,5 vCPU / 1 GB RAM**. Autoscaling выключен. База данных, диск, дополнительные контейнеры, отдельные балансировщики и платные дополнения не нужны. Убедитесь в форме итоговой стоимости, что выбран именно Sandbox и один ресурс.
5. В Runtime variables задайте:

   ```text
   PORT=8080
   TICK_HZ=60
   SNAPSHOT_HZ=20
   MAX_PLAYERS=7
   BOTS=8
   MAX_BOTS=30
   RECONNECT_SECONDS=30
   EMPTY_ROOM_SECONDS=60
   ALLOWED_ORIGINS=https://fen417.github.io
   LOG_METRICS=0
   ```

   Для личного домена укажите его origin вместо GitHub Pages; несколько origin разделяются запятыми, без путей и завершающего `/`. Если allowlist пуст, допускаются любые origin. Это ограничение браузерных источников, не система авторизации друзей.
6. Добавьте **`METRICS_TOKEN`** как секретную runtime-переменную Northflank. Длинную случайную строку можно создать менеджером паролей. Она защищает только статистику, в игру не передаётся. Не добавляйте её в репозиторий, GitHub Pages, `VITE_*` или `network-config.json`.
7. Networking: один **публичный HTTP-порт 8080**, название `game`. Возьмите предоставленный домен `game--…code.run`. Внутри контейнера обычный HTTP; Northflank предоставляет HTTPS/WSS с TLS на публичном порту 443. Никакой дополнительный reverse proxy не нужен. [Публичные порты и WebSocket](https://northflank.com/docs/v1/application/network/configure-ports).
8. В Health checks настройте HTTP `GET /health` на внутреннем порту 8080: startup — задержка 5 с, период 10 с, timeout 3 с, failure threshold 6; readiness — период 10 с, timeout 3 с, threshold 3; liveness — период 30 с, timeout 3 с, threshold 3. Docker HEALTHCHECK также предусмотрен, но probes Northflank настройте явно. [Health checks](https://northflank.com/docs/v1/application/observe/configure-health-checks).
9. Запустите сборку. Лог готовности: `SECTOR 09 authoritative server listening on 0.0.0.0:8080`. Откройте `https://ВАШ-ДОМЕН.code.run/health`: ожидается `ok: true`, `protocol: 23`. Контейнер остаётся запущен постоянно; при пустой комнате игровой таймер отключается, а health/WebSocket доступны.
10. Сохраните публичный адрес **`wss://ВАШ-ДОМЕН.code.run/ws`** для настройки GitHub Pages ниже. После сбоя контейнер запускается заново платформой; вся игровая комната при этом теряется, поскольку состояние намеренно хранится только в RAM.

## Подключение GitHub Pages

Предпочтительный способ: GitHub → репозиторий → **Settings → Secrets and variables → Actions → Variables → New repository variable**:

```text
Name: SECTOR_SERVER_URL
Value: wss://ВАШ-ДОМЕН.code.run/ws
```

Это публичный адрес, ему не нужен статус Secret. Workflow `.github/workflows/pages.yml` подставляет его в `VITE_SERVER_URL` при сборке. Запустите **Actions → Deploy game to GitHub Pages → Run workflow** после добавления переменной. В Settings → Pages источником должен быть GitHub Actions.

Альтернатива без переменной сборки: запишите публичный адрес в `public/network-config.json`, закоммитьте и дождитесь Pages:

```json
{"serverUrl":"wss://ВАШ-ДОМЕН.code.run/ws"}
```

Переменная сборки имеет приоритет над файлом. Сохранённый вручную адрес в меню переопределяет оба варианта для этого браузера. Вернуть значение по умолчанию можно в консоли браузера: `localStorage.removeItem('sector09-server-url')`, затем перезагрузить страницу. Незащищённый `ws://` с HTTPS-страницы запрещён. Production-адреса localhost в конфигурации отсутствуют.

Далее:

1. Первый игрок открывает игру, нажимает **СОЗДАТЬ КОМНАТУ**, задаёт название, карту, режим «Захват территории», лимит 2–7 игроков и 0–30 ботов; по умолчанию 8.
2. Друзья открывают **БРАУЗЕР КОМНАТ** и подключаются. Список обновляется по изменениям без частого polling.
3. Создатель запускает матч из лобби. Он обычный клиент; его выход не прекращает матч. Право запуска следующего матча передаётся оставшемуся игроку.
4. После обрыва клиент автоматически пытается переподключиться в течение 28 с. Место и персонаж сохраняются 30 с. Если остальные играют, отключившийся боец остаётся в мире и может получить урон. При полном отсутствии соединённых игроков время матча замораживается. Пустая комната удаляется через 60 с.

Обновляйте клиент и сервер из одного коммита: протокол и ревизия карт проверяются при подключении. Перезапуск сервера или новый деплой завершает текущую комнату.

## Конфигурация и плавность

| Параметр | Значение по умолчанию | Границы |
|---|---:|---|
| `TICK_HZ` | 60 | 30–60 Гц, независимо от сети |
| `SNAPSHOT_HZ` | 20 | 10–20 Гц |
| Команды клиента | 60 шагов/с | Упаковка примерно в 30 сообщений/с |
| Реальные игроки | 7 | 2–7 |
| Боты | 8 | 0–30, либо меньше через `MAX_BOTS` |
| Буфер интерполяции | 85–180 мс | Адаптируется к джиттеру/RTT |
| Дальние цели | 2–10 обновлений/с | Индивидуальный буфер, без рывков между редкими обновлениями |
| Прицел разведчика | До 20 обновлений/с | Повышенный приоритет целей на карте |
| Экстраполяция | До 80 мс | Только положение, никогда HP/урон |

Клиент немедленно предсказывает движение своего пехотинца и управляемой техники общими функциями коллизий. Сервер подтверждает номер обработанной команды; клиент восстанавливает авторитетное положение и повторяет неподтверждённые команды. Малые поправки пехоты сглаживаются. Боеприпасы, попадания, способности, HP и результаты матча всегда определяет сервер. Клиент не сообщает серверу координаты, HP, урон или скорость. Команды ограничиваются реальным накопленным временем, поэтому отправка лишних команд не ускоряет бойца.

Проверяйте RTT в реальной сети друзей через консоль браузера:

```js
JSON.parse(document.getElementById('game').dataset.networkStats)
```

Видны RTT, буфер интерполяции, его опустошения, очередь команд, стоимость декодирования/коррекции и принятые байты. В `dataset.renderStats` доступны p95/p99 времени кадров, CPU, симуляции и отправки рендера, а также число кадров длиннее 50/100 мс в последнем окне до 300 кадров. Время рендера здесь измерено на CPU, это не GPU timer query. Сервер публикует p95/p99 тика и задержки цикла в окне до 600 отсчётов. Это внутриигровой WebSocket RTT, а не ICMP ping. При необходимости сравнивайте регионы последовательно, предварительно удаляя старый сервис; смена региона требует другого проекта. Минимальный пинг из Приднестровья без измерений не обещается.

Для существующего развёртывания измените переменную `MAX_BOTS=12` на `MAX_BOTS=30` и пересоберите сервер из новой версии. Без этой переменной новый максимум по умолчанию — 30; значение `BOTS=8` задаёт только начальный выбор. Повышение лимита не является замером производительности сервера с 30 ботами.

## Протокол и оптимизация

Подробная схема — в [docs/network-protocol.md](docs/network-protocol.md).

- Только редкие управляющие сообщения используют JSON: комнаты, лобби, настройки, старт, высадка и статистика. Весь динамический матч и события бинарные.
- Снимок содержит sequence ID, подтверждённую базу, обработанную команду и маски изменившихся полей. Дельта строится относительно **подтверждённого**, а не последнего отправленного состояния. Базы хранятся ограниченной историей. Полный снимок — при входе, запросе resync и раз в 5 с.
- Строки заменяются 16-битными ссылками на словарь; определения передаются до подтверждения. Координаты бойцов/техники — 16 бит относительно границ карты; высота — 1/128 м; углы — signed16. Симуляция и расчёт попаданий сохраняют исходную точность. Точки попаданий, ракеты и гранаты используют float32 там, где это необходимо.
- Здоровье, оружие, имена, экипировка, неподвижная техника и точки не пересылаются повторно при отсутствии изменений. Таймеры передаются как срок окончания, а не новый остаток на каждом снимке.
- Игроки остаются в ростере/таблице счёта и на карте. Близкие и активно стреляющие цели обновляются чаще, дальние — реже. Далёкие гранаты и ракеты фильтруются; собственные снаряды и важные результаты сохраняются. Геометрия и ресурсы через WS не передаются.
- Выстрелы, попадания, смерть, урон, перезарядка, смена оружия и прочие события отправляются на ближайшем тике, независимо от большого снимка. Результаты сохраняются до ACK; устаревшая база событий вызывает переподключение с полной синхронизацией.
- При очереди WS свыше 8 KiB необязательный снимок пропускается до кодирования. События ожидают освобождения очереди, а не исчезают. Длительно отстающий клиент отключается и переподключается вместо неограниченного накопления данных. `permessage-deflate` выключен.
- Статическая сетка коллизий используется и при поиске опоры под ногами, вместо полного перебора всех объектов на каждого бойца. Ранее существовавший пространственный raycast сохранён. У ботов остаются разнесённые по времени наблюдение и решения; сервер ограничивает новые запросы маршрута одним на тик. Незавершённые поиски продолжаются по очереди в пределах общего бюджета, укрытия и этажи индексируются пространственно. Проверки ближайших бойцов остаются прямыми.

На перегруженном процессе выполняются максимум три догоняющих шага фиксированной длительности. Просроченные целые шаги отбрасываются; увеличенного шага физики до 100 мс больше нет. Длительные зависания не компенсируются неограниченным циклом; отброшенное при них время видно в `droppedSimulationSeconds`. После конца раунда частый цикл также отключается до следующего запуска. Если измерения показывают систематическое превышение 16,7 мс, сначала уменьшите ботов, затем при необходимости `TICK_HZ` до 45/30. Физика использует dt; это не переключение всей игры на замедленное время.

## Фактический трафик и CPU

`GET /metrics` требует `Authorization: Bearer METRICS_TOKEN`. Если секрет не задан, доступ разрешён только с loopback внутри контейнера. Endpoint не публикует токены игроков. Есть:

- `bytesPerSecond`, `messagesPerSecond`, `totalBytes`, `totalMessages`;
- `averageSnapshotBytes`, `skippedSnapshots`, `overruns`;
- `tickAverageMs`, `tickMaximumMs`, `cpuCorePercent`, `rssBytes`, `droppedSimulationSeconds`;
- для каждого игрока — байты/с, суммарные байты и средний снимок.

Окно усреднения — 5 с. `cpuCorePercent: 50` означает примерно половину одного полного ядра, а не 50% выделенного лимита. Для 0,5 vCPU это уже около всей квоты; локальные измерения не заменяют метрики контейнера с CPU throttling.

Способ просмотра без размещения токена в браузере: Northflank → сервис → контейнерная консоль, переменная `METRICS_TOKEN` уже доступна процессу:

```sh
node scripts/server-traffic.mjs http://127.0.0.1:8080 60
```

В runtime-образ включён этот небольшой скрипт. Последнее число — ожидаемые активные часы игры за месяц, не длительность проверки. Он делает один запрос метрик и считает прогноз. Для внешнего запроса запустите тот же скрипт с HTTPS-адресом сервера, передав секрет через переменную окружения `METRICS_TOKEN` на своём компьютере. Это просмотр статистики удалённого сервера, не размещение игры на ПК.

Альтернатива — `LOG_METRICS=1`: одна компактная запись каждые 5 с в логах сервиса. Для постоянной работы оставляйте 0. Счётчики учитывают полезную нагрузку WS и заголовок исходящего WS-кадра; TLS/TCP/IP, retransmits и трафик инфраструктуры не учитываются. Для оплаты окончательны показатели Northflank Billing/Networking.

## Sandbox, расходы и уведомления

Условия сверены 13.11.2026. На [странице тарифов Northflank](https://northflank.com/pricing) Sandbox описан как бесплатный ресурсный бюджет до $20/месяц, с постоянно работающими сервисами. `nf-compute-50` стоит около **$0,01667/ч = $12 за 720 ч**. Исходящий трафик — **$0,06/GB**, входящий бесплатный. Условия и фактически доступная квота вашего аккаунта могут отличаться: проверьте Billing перед созданием. Страница тарифов говорит «без карты», а общая billing-документация упоминает платёжную верификацию; если интерфейс предлагает платный план или обязательную покупку, эта инструкция её не требует.

Расчёт по серверным байтам (десятичный GB):

```text
egress_GB = измеренные_байты_в_секунду × активные_часы_в_месяц × 3600 / 1e9
compute   = 0.01667 × часы_работы_контейнера
прогноз   = compute + egress_GB × 0.06 + сборки/прочие начисления Northflank
```

Пример **при измеренном общем исходящем 1 Мбит/с**, а не обещание текущей производительности:

| Активная игра | Egress за месяц | Compute + egress за 720 ч |
|---|---:|---:|
| 2 ч/день, 60 ч | 27 GB | около $13,62 |
| 4 ч/день, 120 ч | 54 GB | около $15,24 |
| Непрерывно, 720 ч | 324 GB | около $31,44 |

При 2 Мбит/с стоимость трафика удваивается. В 31-дневном месяце 744 runtime-часа стоят около $12,40. Из $20 после compute за 720 ч остаётся около $8, то есть примерно 133 GB egress **без запаса на сборки и сетевые накладные расходы**. Цель 1–2 Мбит/с — ориентир оптимизации, а не подтверждённый результат для семи игроков на Northflank.

В Northflank → аккаунт/команда → **Billing** настройте billing alerts, например $12, $16 и $18, на свой email. Контролируйте текущий и прогнозируемый расход проекта/сервиса. Официально описаны уведомления по email и настроенным интеграциям; [billing alerts](https://northflank.com/docs/v1/application/billing/monitor-spending) **не являются гарантированным автоматическим отключением по бюджету**. Платёжный billing threshold также не является лимитом расходов. Подтверждённого отдельного пользовательского hard cap для этого Sandbox в изученной документации нет; при приближении к квоте остановите сервис или сократите время игр. Автоматические top-up и переход на платный план не включайте. Никаких ресурсов в вашем аккаунте эта работа автоматически не создаёт.

## Практические ограничения

- Реализован существующий режим Conquest; других игровых режимов в движке нет. Поле режима показывает его явно.
- Комната одна, память непостоянная. Деплой/перезапуск уничтожает матч; миграции между процессами нет.
- Авторизация друзей и античит уровня соревновательной игры не добавлялись. Сервер проверяет команды, время движения, патроны, попадания и урон, но специального rewind попаданий по историческим позам нет. Высокий RTT заметен при стрельбе по движущимся целям.
- 7 игроков + 8 ботов — целевая конфигурация, не подтверждённая гарантия 60 Гц на Sandbox. Длительный стресс-тест не проводился. На «Сухом ветре» сравнивайте tick/cpu метрики с остальными картами; до 30 ботов разрешены настройкой, но не объявлены безопасным максимумом по CPU.
- Клиентское предсказание компенсирует перемещение и вождение, а не серверные последствия стрельбы. Позиции других машин для локальных коллизий берутся из последних серверных данных, поэтому контакт движущейся техники может требовать коррекции.
- Реальное развёртывание требует доступа владельца к Northflank и выбора URL. Без созданного сервиса и WSS-адреса GitHub Pages показывает понятное сообщение о настройке сервера; одиночный режим доступен.
